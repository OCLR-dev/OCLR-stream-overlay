## 7. abort 后确认重赛，自动化未接回

- 现场流程：进图约 15 秒内有人卡住，裁判 `!mp abort`，重新 ready；直播员在再次 start 前点击「裁判已要求重赛本图」。随后画面／分数能跟随，自动计胜和后续 Pick 却无法正常继续，最终通过手工开打／结束／改分／记胜推进。

## 8. 保留逐图修正备用，直接修改系列比分即可继续

- 用户反馈：直播员通常直接调整系列比分，「已记某队胜 · 修正」不应成为恢复自动化的必经步骤。最终选择：保留逐图修正备用，直接改比分应能正常继续。
- 服务端修复：本图已进入结算，或连续观察到当前同房间同谱面 Playing → Ranking 后，直播员直接修改系列比分会将本图标记为「已按系列比分处理」，解除本图待核对异常并仅开放一次下一 BP。只接受当前有效来源佐证的结束状态；外部请求不能自行指定结束局次。
- 直接系列分是实际累计基准，不从总比分差猜单图胜方，不制造 run 或最终队分。旧 Ranking 不会再次补记赢图；下一实际比赛照常自动开打、结算并从校正比分继续累计。之后若通过备用接口补注本图胜方，不再额外增加一次系列分。
- 正在 Playing、重赛尚未开打、明确暂停，或没有结束证据时，修改系列分只改累计值，不提前结束本局或取消未解决异常。首次接入、断线和超过五秒的观察缺口不借用旧显示证据。重复校正不重复消费 BP，撤销可恢复校正前状态。
- 界面改动仅保存在隔离副本及本地可审查补丁：逐图「修正」加「备用」说明；系列分输入成为主修正路径。明确重新输入同一个正确比分也提交一次核对；已处理本图不再出现在待人工记胜列表，图池显示已打，并提示可以继续下一图。修正后顶部不再残留旧的「异常挂起」说明。

## 9. Panic 重载房间后比分消失，必须手动恢复原局

- 用户反馈：比赛端点击 Panic 重新加载房间，正在进行的本图不再显示比分，必须到控制台点击恢复原局；这种二次操作不合理。
- 根因：`liveTeamScores` 将 `session.incident` 直接作为隐藏实时比分的条件；观战窗口重建触发自动待核对后，即使新鲜 Playing／Ranking 和实际队分恢复，显示仍然被屏蔽。原自动观察器又将所有异常统一保持为必须人工恢复，未区分能核验的观战重载。
- 官方依据：[osu!tourney Panic 说明](https://osu.ppy.sh/wiki/en/osu%21_tournament_client/osu%21tourney/Spectator_usage) 指明其作用为重新初始化观战实例。[tosu v2 类型](https://raw.githubusercontent.com/tosuapp/tosu/master/packages/tosu/src/api/types/v2.ts) 提供 IPC、选手、分数等快照，没有单独 Panic 按钮事件。因此实现按本次观战恢复的实际证据接回，不声称能直接读取用户点了该按钮。

### 修复与边界

- 实时比分与自动计胜分开：收到新鲜有效 Playing／Ranking 房间快照，即显示其当前实际队分，待核对状态不再将其隐藏。显示分数不清除异常、不补造开打／胜方、不解除人工等待；过期、断线、初始化及空房间继续不显示实时分数，不拿旧帧填充。
- 服务端新增易失的观战恢复上下文，只在当前已开打局的完整 Playing 中建立锚点。重载期间允许初始化、谱面暂空、窗口／选手部分缺失；恢复后必须同比赛、同局、同 run、同谱面、同房间／左右队伍与完整原组选手，选手分数有效、不低于重载前值，且每侧选手分数之和与队分一致。
- 连续两次完整 Playing、相隔至少 250ms 后，自动清除这次来源为 tosu 的未知观战异常，并重建观察位置，沿用原 run、Pick、BP 与 EX。恢复动作本身不加赢图、不创建重赛。随后新的 Playing → Ranking 正常结算，只记一次，并继续下一 Pick。
- 恢复上下文最多保留 30 秒，相邻帧静默超过 5 秒即失效，不写入持久化或从重启加载。明确 ready／Idle、Ranking、换图、换房、已更换局次、明确暂停、人工待核对／裁判重赛和传输连接中断不会被这一恢复路径自动放行。直接恢复到旧 Ranking 不补记胜方。
- 即使恢复证据不足，新的真实队分仍可显示；只有未能核验的赛果和裁判决定保留人工处理。此前文档中「Panic 一律需要再点恢复原局」的描述由本条取代；真实 abort／重赛继续使用第 7 条流程。
